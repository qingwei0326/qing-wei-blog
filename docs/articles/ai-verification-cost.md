# 没验证就汇报，是 AI 协作里最贵的坏习惯

这次改博客，我被自己的一句话提醒了：

> 你要验证完再来报告，没验证来加剧工作量呢。

这句话不是在催进度，它讲的是一个很具体的协作成本：**没验证就汇报，不是在交付结果，是把不确定性转交给对方。**

![AI 协作验证流程对比](/images/ai-verification-cost-image2.webp)

下面按这次改版的时间顺序，记下每一步踩了什么坑、后来补了哪层验证。

---

## 第一步：想把首页调好一点

我原本只是想把博客首页调好一点，流程看起来很简单：

1. 看首页截图
2. 改 `HomeBoard.vue`
3. 跑构建
4. 本地预览
5. 截图确认

## 第二步：构建通过了，但页面不对

**坑 1：构建通过，不代表页面可用。** VitePress 构建成功了，但本地预览端口上可能还挂着旧进程。结果 HTML 是新的，CSS / JS 资源却对不上。只看一句 `build complete` 就汇报，对方打开页面看到的是 404 或旧样式。

**坑 2：截图生成，不代表视觉正确。** 移动端截图确实生成了，但标题被挤成奇怪的长行，推荐卡右侧看起来被裁掉。文件存在、命令成功、页面 200，都不能证明它好看。

**坑 3："差不多了"最贵。** 页面设计不是代码题。代码不报错，机器就觉得能跑；但用户看到的是排版、比例、阅读节奏、有没有别扭感。这里不能靠"应该可以"，得打开看。

## 第三步：补上四层验证

这次改版里，真正有效的验证至少有四层：

| 层 | 命令 / 动作 | 挡掉什么 |
|---|---|---|
| 1. 数据校验 | `pnpm run docs:check` | frontmatter、封面路径、正文图片路径、permalink 重复 |
| 2. 生产构建 | `pnpm run docs:build` | 开发模式能跑、生产构建才暴露的问题 |
| 3. 资源检查 | 查首页、文章页、最新 CSS 是否 200 | "HTML 是新的，CSS 没加载"的假正常 |
| 4. 截图复核 | 桌面端、移动端、文章页、特殊配置 | 排版和视觉问题 |

几点补充：

- **生产构建**：这次有一个大 chunk 警告，但不是失败。之前尝试随手拆包，反而引发主题初始化问题。所以这类警告要记录，但不能为了"看起来干净"乱改。
- **资源检查**：为什么要查 CSS？因为静态站最容易出现页面能打开、样式全乱的假正常。
- **截图复核**："博客全图"是特殊配置，默认首页看起来正常，不代表切到"全图"预设也正常。后来强制切到 `wide` 预设再截图，才确认原来那种深色整图背景裁切确实被改掉了。

## 第四步：什么时候可以汇报

我现在的标准：**不是命令跑完就汇报，而是能回答"你验证了什么"再汇报。**

这次能说清楚：

- `docs:check` 通过，10 篇文章校验正常
- `docs:build` 通过，只有已知的大 chunk 警告
- 首页、文章页、最新 CSS 都是 200
- 桌面、移动端、文章页、`wide` 预设都截图看过
- 本地预览在 `4173` 跑着

这才叫交付，否则只是"我这边感觉差不多"。

## 回头看：几句话别混着说

AI 很擅长给你一个"完成感"，但这四句话不是一回事：

| 说法 | 真正应该代表什么 |
|---|---|
| 已修复 | 代码改了，并且目标问题消失 |
| 已优化 | 视觉 / 体验比原来更好，而不是只是 CSS 变多了 |
| 已构建 | 生产构建通过，警告可解释 |
| 已验证 | 页面、资源、核心路径、截图都看过 |

最危险的是把"我做了"说成"它好了"，这两个差一轮验证。

## 这笔账怎么算

一次没验证的汇报，看起来省了 2 分钟，但后面可能多出来：

| 后续成本 | 时间 |
|---|---|
| 用户打开页面发现不对 | 2 分钟 |
| 截图发回来解释 | 3 分钟 |
| 重新定位问题 | 10 分钟 |
| 再构建、再预览、再截图 | 5 分钟 |
| 信任损耗 | 不好量化，但最贵 |

**省 2 分钟，亏 20 分钟。** 所以我更认可一个慢一点但完整的闭环：

> 改完 → 构建 → 重启预览 → 查资源 → 截图 → 看截图 → 再汇报。

## 对人也一样

这件事不只适用于 AI。我以前最烦的工作方式是：对方发来一句"好了"，然后你要问：哪个环境？哪个地址？你跑过没有？截图呢？有没有影响旧页面？

真正有用的汇报应该像这样：

> 我改了 A / B 两处；本地构建通过；生产路径 `/xxx/` 打开正常；移动端 390px 截图看过，没有横向滚动；剩一个警告是 chunk 过大，不影响运行。

这段话长一点，但省掉后面十轮问答。

## 这篇的局限

- **"省 2 分钟，亏 20 分钟"是我这次的估算，** 不是统计数据，各项耗时我没有精确计时。
- **文中的验证方法针对 VitePress 静态站，** 其他项目需要换成对应的检查。
- **本文的验证清单不能保证没有问题，** 只能把"没看过就汇报"这种可避免的错误挡掉。

## 一句话

> AI 协作不是让它更快地说"好了"，而是让它更稳定地交出"确实好了"。
